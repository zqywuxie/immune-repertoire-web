## 本次数据结构变化

新增 `project_datasets` 表，记录项目、不可变 scope、显示名称、说明、来源、批次、归档、revision及更新时间；按项目/scope唯一。关联沿用已有资产、登记、分组、SQL/Mongo任务的旧scope字符串，显示名修改不改历史引用。

现有应用初始化执行 `db.create_all()`，在新表不存在时创建它；这不是自动修改已有列的通用迁移工具。此次没有旧表列变更，无需批量改写历史数据。数据库账号需具备当前应用已有建表权限。旧数据集在首次保存说明前仍从输入目录汇总；无强制全量回填。

新任务额外保存已有上传内容版本号和原文件名。旧任务未记录该字段时显示“未记录”，不补造版本。新归档不删除输入/结果，不取消任务；它整理默认候选列表，显式历史范围仍可读取。

## 固定更新顺序

1. 在无活动分析的维护时段，按现有七卷冷备流程保存数据库、上传、结果与参考资料；`.env`单独安全保存，不写进发布记录。记录备份位置与恢复版本。
2. 记录当前源码提交、运行中的api/web镜像ID和实际基础运行时镜像ID。保留旧API和网页镜像标签，避免普通build覆盖唯一可回退镜像。
3. `bash init-env.sh`：检查干净工作区并拉取当前远端分支；已有`.env`完整保留。新配置项应对照`.env.example`逐项补入，不能覆盖密码或数据路径。
4. 编辑`.env`，检查HTTP绑定与端口、三个数据路径、UID/GID、两任务并发及每worker资源、认证模式。新增数据集功能无需新增环境变量。
5. 普通代码更新运行 `bash deploy.sh`，它不拉取Git；复用基础镜像，构建API与网页应用层。替换前启用维护并检查活动任务，初始化卷权限，等待健康检查。失败保留配置和卷。
6. 健康之后验证：原项目可读、输入原版可下载、旧任务及结果可读、两worker注册、数据集显示名修改和归档恢复、新小型任务可执行。不要用生产数据跑回归。

## 依赖更新与离线部署

只有依赖清单改变时构建新的运行时镜像标签；普通Python/R脚本、网页修改不重装整个R环境。完整应用Dockerfile在构建中检查运行时清单及科学依赖，不一致时先修正基础镜像，不绕过检查。

在可联网机器按部署指南构建基础镜像/API/网页，`docker save`导出所需标签，服务器`docker load`导入；`.env`的`ANALYSIS_RUNTIME_IMAGE`必须与导入标签一致。保存镜像包含依赖，Git更新仅包含代码；网页访问仍须内网或SSH隧道。

## 回退

保留旧镜像时，在维护状态且无活动任务后将旧API镜像重新标记为Compose当前API标签，并将旧网页镜像重新标记为当前网页标签，再执行：

```bash
docker compose --env-file .env -f compose.docker.yml up -d --no-build --wait --wait-timeout 300
docker compose --env-file .env -f compose.docker.yml ps
```

不要执行`down -v`或删除数据库。旧版本可以忽略新增`project_datasets`表，原scope数据未改变；新增说明/归档在旧界面不展示，表保留以供再次升级。回退后验证旧项目/输入/结果、worker与维护状态；如果部署退出提示维护解除失败，按deploy.sh打印的实际token解除，不能凭空写一个token。

若未来发生不兼容列迁移，必须另提供迁移/回退程序；镜像回退不能当作数据库回退。灾难恢复使用已验证的七卷冷备工具，MySQL整个数据卷包含新增表；本次还未重做“含新表”的完整冷恢复，不能称新版冷恢复已经通过。
