## 二、把上游产物真正接到下游

按实际运行模式定义输入与输出，不再仅判断是否上传了原始克隆表。

| 下游分析 | 实际需要的前置数据/产物 |
|---|---|
| 样本指标、组成分析 | 筛选后的样本指标与分组表 |
| 克隆共享、优势克隆等 | 匹配样本的克隆数据及相应样本表 |
| V/J 差异、特征降维 | 克隆共享/分类后生成的使用频率或汇总特征矩阵 |
| 特殊 T 细胞分析 | 带分类信息的受体 α 链结果及参考数据 |
| 机器学习 | 按所选模式使用样本指标或已生成特征；仅已接入的模式可运行 |
| 转录组差异 | 表达矩阵和样本分组 |
| 基因功能与通路富集 | 匹配比较条件的差异分析结果 |
| 免疫浸润组成/比较 | 浸润结果表和样本分组 |
| 免疫浸润一致性/通路关联 | 按具体面板检查第二种估计、表达矩阵、通路或富集结果 |

实施方式：

1. 扩展现有任务结果、项目资产和结果清单，不另建任务引擎。记录产物类型、来源任务、项目、数据集、输入资产标识、适用链/分组/比较条件及状态。
2. 候选查询按项目、数据集和下游模式筛选；仅比较该模式真正需要的条件。旧结果缺少来源信息时显示“需确认来源”，不直接当作匹配结果。
3. 唯一匹配结果可预选并展示来源；多个匹配结果让用户选择，显示来源任务、时间与分析条件，不静默覆盖用户选择。
4. 前端提交产物标识，后端解析路径；提交与执行时复核所属范围、任务成功状态、适用条件和文件存在。保留已有任务请求的兼容读取，禁止跨数据集混用。
5. 结果页增加“继续分析”，携带已选产物进入下游；缺结果时提供“前往完成前置分析”，保留目标页面和项目上下文。不在浏览页面时自动启动计算。
6. 现有富集模块内部可以直接从表达矩阵计算差异。保留这条可运行路径，并使中间差异结果可登记和复用；增加读取兼容差异结果的路径后，再显示“复用已有差异结果”。不只改前端提示就宣称已打通，不混用不同统计方法或比较条件。
7. 浸润模块通过现有工作进程接入参考脚本，按面板分别校验依赖。完成实际任务、结果登记和容器回归后才展示为可运行；只增加上传框不算完成第四类数据分析闭环。

## 五、分析进度与结果展示（追加需求）

现状依据：`Stage4Execution.tsx` 轮询任务并重复追加状态日志；`JobDetailPanel.tsx` 已有进度历史；`background_job_service.py` 已保存进度、阶段、详情与终止状态；`useJobEvents.ts` 有任务事件连接。`Stage5Results.tsx` 与 `JobResultPanel.tsx` 各有结果展示，后者主要用下拉选择文件并打开外部页面。改造复用这些接口及 `features/results/ResultViewer.tsx`，保持两类任务契约。

### 进度：看清实际执行状态

1. 任务页顶部固定分析名称、项目/数据集、总体状态、开始时间和已耗时。主体按本次真实执行计划显示步骤，例如“检查输入 → 准备数据 → 分析计算 → 生成图表 → 整理结果”；无需执行的步骤明确为复用或跳过。
2. 每步展示等待、执行中、完成、失败等状态，正在执行的步骤展开显示当前链、分组或处理数量（仅在后端提供时）。独立任务和组合分析共用视觉组件；组合分析同时展示各子任务状态和依赖等待原因。
3. 有实际可计数工作量时显示完成数和百分比；只能确定阶段时显示阶段进度与已耗时，不按时间伪造百分比或剩余时间。结果尚未登记完成时显示“正在整理结果”，不提前标记成功。
4. 连接断开时保留最近状态，显示最后更新时间和重连提示；恢复后重新读取任务快照。刷新或离开页面后可按任务地址继续查看，不因前端消失就丢失任务，也不再次提交同一任务。将 interrupted 等后端终止状态纳入所有进度入口，终态停止轮询。
5. 日志默认折叠，按状态变化追加并去重；常规提示使用中文，技术日志留在详情。失败卡显示失败步骤、可操作原因及“修改参数后重试”；实际停止确认前显示“正在取消”。重试生成新任务并保留原记录，不宣称支持尚未实现的断点续算。
6. 组合分析出现失败时保留已成功结果；依赖失败节点的下游显示不能继续的原因。批次总状态依据全部已提交/待执行子任务计算，不能仅因已收到的结果全部成功就提前显示整批完成。

### 结果：先看分析内容，再管理文件

1. 默认展示结果概览：来源项目/数据集、实际输入和前置结果、所选分组/比较、运行状态与已生成内容。统计摘要仅展示结果文件提供的指标，不自动编造生物学结论。
2. 页面分为“图表、数据表、分析详情”；报告作为图表区或独立报告入口。按分析内容、链和比较分组组织，而非让用户只凭原始文件名寻找结果。

4. 单图、单表和整项分析结果分别下载。批量下载采用一次归档下载或现有归档接口，避免逐文件弹出多个窗口；技术清单和文件路径置于详情。

6. 结果页提供“继续分析”，直接带入已登记产物与适用条件；与第二节共用来源校验。历史任务也采用相同结果组件，按项目、数据集、分析类型和状态筛选，结果地址保留当前图表/比较选择以支持刷新返回。

## 六、Linux 服务器部署审视（追加需求）

本节为源码与配置审视，不代表已在目标服务器验收。现有 Linux 容器、容器服务名、独立计算工作进程和命名卷是迁移基础；目标服务器仍需完成空环境部署、数据恢复及真实任务验证。

### 部署前必须处理

1. **内部访问模式与服务器入口。** 当前 `compose.docker.yml` 只绑定本机网页端口，数据库不暴露宿主机端口，应保留该边界。免登录模式通过内网、虚拟专用网络或受控反向代理访问；不要把“隐藏账号页面”等同于允许任意公网访问。需要公网开放时配置域名、加密连接和入口访问控制，与内部共享模式区分。补齐可信代理头及登录模式回归，按实际代理拓扑配置，不盲目信任全部转发头。
2. **干净服务器可复现启动。** `docker/init-env.ps1` 是 Windows 初始化入口，增加可在容器中运行的跨平台配置生成命令及 Linux 部署说明。完整分析镜像必须显式选择；默认配置生成器目前不填写完整镜像选项。按目标处理器架构验证科学计算依赖，避免将本机可用镜像误当作任意 Linux 服务器都可运行。固定发布镜像版本，保留回退版本；前端镜像构建不等于前端测试已执行，发布流程显式跑测试阶段。
3. **代码、参考库与业务数据完整迁移。** 当前 Dockerfile 仅复制 flask_app、analysis_workers、选定 scripts 和 docker/app，外部 `immune_pipeline` 不在镜像中。新增模块所需脚本应以明确版本打包到镜像，运行所需配置与清单逐项验证是否在构建上下文；参考库用固定容器路径挂载，记录版本。检查历史资产、任务参数及结果清单中的宿主机路径和绝对路径；不依赖 Windows 目录联接。已有迁入 `/app/flask_app/data` 的路径保持容器内一致，迁移后抽查输入、结果和下载。
4. **备份与恢复。** 当前部署说明记录的是迁移快照；`snapshot_mysql.py` 明确要求数据库停止，不能直接当作在线定时备份。制定数据库与业务文件一致的备份方式、保留周期及异机副本，新增数据纳入后续备份。在空卷恢复并验证项目、任务、文件引用和下载；镜像传输不能替代数据卷迁移。
5. **资源与长任务。** Compose 未配置计算资源上限和日志轮转。增加计算进程的内存、处理器、进程数及并发配置，给数据库和网页服务留出资源；按模块设任务超时，避免所有分析一律 7200 秒。先以小并发测量峰值，不直接增加网页进程数，当前 Dockerfile 明确存在进程内旧任务注册表限制。工作进程健康检查应检查自身心跳，当前“存在任意工作进程”在扩容时不足以证明该实例健康。补充整机重启后的任务对账，未完成任务应恢复可识别状态，不能显示假完成或无限运行。
6. **上传与存储权限。** 网页代理与 Flask 当前均限制 100 MB，按预期输入规模同步调整；大数据提供受控服务器导入，分片上传仅在实际文件规模证明有需要时增加。Linux 挂载目录验证用户/组权限、中文与空格路径、文件名大小写；脚本执行权限和换行也纳入验收。当前完整分析镜像以 root 运行，改为专用运行用户时同时处理数据卷和图形/文档临时目录权限，不能仅加 USER 导致任务无法写文件。

### 稳定后按需要优化

- 完整镜像同时包含分析、网页接口与文档处理依赖。先保持可运行，再评估将接口和计算镜像分别发布、复用依赖层；不为缩小镜像删除分析依赖或参考数据。补充传递依赖、R 包及模型版本记录，离线准备受限网络所需镜像和参考资料。在线通路注释的依赖与失败状态应明确，记录实际注释版本或获取时间。
